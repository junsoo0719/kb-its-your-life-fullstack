# ✨ 스프링 컨텍스트 - 빈 작성

## 1. 스프링 빈 간의 관계 설정

스프링 컨텍스트에는 여러 빈을 등록할 수 있고, 빈 사이의 관계도 설정할 수 있다.

예를 들어 다음과 같은 관계를 만들 수 있다.

1. 스프링 컨텍스트에 앵무새와 사람을 빈으로 추가한다.
2. 사람이 앵무새를 소유하도록 설정한다.

즉, `Person` 빈이 `Parrot` 빈을 가지는 구조를 만들 수 있다.  
이런 관계를 객체 관점에서는 has-A 관계라고 볼 수 있다. 📌

## 2. has-A 관계

has-A 관계는 한 객체가 다른 객체를 속성으로 가지는 관계이다.

예를 들어 사람이 앵무새를 소유한다면 다음과 같은 구조가 된다.

    public class Person {
        private Parrot parrot;
    }

이 경우 `Person`은 `Parrot`을 가진다.  
즉, `Person has a Parrot` 관계이다.

스프링에서는 이런 객체 간 관계를 빈 사이의 의존성으로 설정할 수 있다.

## 3. 구성 파일에서 빈 간 관계 구현

구성 클래스 안에서 `@Bean` 메서드를 사용하면 빈을 직접 정의할 수 있다.

그리고 한 `@Bean` 메서드 안에서 다른 `@Bean` 메서드를 호출해 빈 사이의 관계를 만들 수 있다.

예를 들면 다음과 같다.

    @Configuration
    public class ProjectConfig {

        @Bean
        public Parrot parrot() {
            Parrot p = new Parrot();
            p.setName("Koko");
            return p;
        }

        @Bean
        public Person person() {
            Person p = new Person();
            p.setName("Ella");
            p.setParrot(parrot());
            return p;
        }
    }

이 코드에서 `person()` 메서드는 `parrot()` 메서드를 호출해서 `Person` 객체 안에 `Parrot` 객체를 설정한다.

결과적으로 사람 빈과 앵무새 빈 사이에 has-A 관계가 만들어진다. ✅

## 4. @Bean 메서드 직접 호출 시 동작

`@Bean`으로 지정된 `person()` 메서드에서 `@Bean`으로 지정된 `parrot()` 메서드를 호출하면 스프링은 단순한 자바 메서드 호출처럼만 처리하지 않는다.

흐름은 다음과 같이 이해할 수 있다.

1. `person()` 메서드에서 `parrot()` 메서드를 호출한다.
2. 스프링 컨텍스트에 이미 앵무새 빈이 있는지 확인한다.
3. 이미 있다면 실제 `parrot()` 메서드를 다시 실행하지 않고, 컨텍스트에 있는 앵무새 빈을 반환한다.
4. 없다면 `parrot()` 메서드를 호출하고, 반환된 값을 컨텍스트에 추가한 뒤 반환한다.

즉, 스프링은 `@Bean` 메서드 호출을 가로채서 같은 빈이 중복 생성되지 않도록 관리한다. 📌

## 5. 두 번째 Parrot 인스턴스가 생성되는가?

설정 클래스가 스프링에 의해 관리되는 경우, `@Bean` 메서드 간 호출은 스프링이 관리한다.

따라서 다음 흐름처럼 보이더라도 일반적으로 두 번째 `Parrot` 인스턴스가 새로 만들어지는 것이 아니다.

1. 스프링은 `parrot()` 메서드를 호출해 앵무새 빈을 생성하고 컨텍스트에 추가한다.
2. 스프링은 `person()` 메서드를 호출해 사람 빈을 생성하고 컨텍스트에 추가한다.
3. `person()` 안에서 `parrot()`을 호출해도 스프링 컨텍스트에 있는 기존 앵무새 빈을 반환한다.

즉, 스프링이 설정 클래스를 관리하는 상황에서는 컨텍스트에 등록된 빈을 재사용한다. ✅

## 6. @Bean 메서드 매개변수로 빈 와이어링

빈 간 관계를 설정하는 또 다른 방법은 `@Bean` 메서드의 매개변수로 필요한 빈을 받는 것이다.

예를 들면 다음과 같다.

    @Configuration
    public class ProjectConfig {

        @Bean
        public Parrot parrot() {
            Parrot p = new Parrot();
            p.setName("Koko");
            return p;
        }

        @Bean
        public Person person(Parrot parrot) {
            Person p = new Person();
            p.setName("Ella");
            p.setParrot(parrot);
            return p;
        }
    }

이 방식에서는 스프링이 `person()` 메서드를 호출할 때 컨텍스트에서 `Parrot` 타입 빈을 찾아 매개변수로 전달한다.

즉, 메서드 매개변수를 통해 스프링에게 필요한 의존성을 제공하도록 지시하는 방식이다. 📌

## 7. 와이어링의 의미

와이어링은 빈과 빈 사이의 관계를 연결하는 것을 의미한다.

예를 들어 `Person` 빈이 `Parrot` 빈을 필요로 한다면, 스프링이 `Person` 안에 `Parrot`을 넣어 주는 과정이 와이어링이다.

결과적으로 두 빈 사이에는 다음과 같은 관계가 생긴다.

- `Person` 빈
- `Parrot` 빈
- `Person`이 `Parrot`을 소유하는 has-A 관계

즉, 와이어링은 객체 사이의 의존 관계를 스프링이 연결해 주는 작업이다. ✅

## 8. IoC를 사용하지 않는 경우

IoC를 사용하지 않는 경우에는 애플리케이션이 필요한 의존성을 직접 생성하고 제어한다.

예를 들면 다음과 같다.

    Parrot parrot = new Parrot();
    Person person = new Person();
    person.setParrot(parrot);

이 방식에서는 개발자가 직접 객체를 만들고, 직접 관계를 설정한다.

즉, 객체 생성과 의존성 연결을 애플리케이션 코드가 직접 제어한다.

## 9. IoC를 사용하는 경우

IoC는 Inversion of Control, 즉 제어의 역전을 의미한다.

IoC를 사용하면 애플리케이션이 직접 의존성을 생성하고 연결하는 것이 아니라, 프레임워크가 객체를 생성하고 관계를 설정한다.

즉, 애플리케이션은 프레임워크에 의해 제어되어 실행된다.

스프링에서는 스프링 컨텍스트가 객체 생성과 의존성 주입을 담당한다. 📌

정리하면 다음과 같다.

- IoC 사용 X → 애플리케이션이 객체 생성과 의존성 제어
- IoC 사용 O → 프레임워크가 객체 생성과 의존성 제어

## 10. @Autowired 필드 주입

`@Autowired`를 필드에 붙이면 스프링이 컨텍스트에서 필요한 빈을 찾아 해당 필드에 직접 주입한다.

예시는 다음과 같다.

    @Component
    public class Person {

        @Autowired
        private Parrot parrot;
    }

여기서 `@Component`는 스프링이 `Person` 타입의 빈을 생성하고 컨텍스트에 추가하도록 지시한다.

그리고 `@Autowired`는 스프링이 컨텍스트에서 `Parrot` 타입 빈을 찾아 `parrot` 필드에 설정하도록 지시한다.

이렇게 하면 두 빈 사이에 관계가 설정된다. ✅

## 11. 필드 주입의 특징

필드 주입은 코드가 짧고 간단해 보인다.

하지만 필드에 직접 값을 주입하기 때문에 객체 생성 시 필요한 의존성이 명확하게 드러나지 않을 수 있다.

즉, 테스트나 유지보수 관점에서는 생성자 주입보다 덜 권장되는 경우가 많다.

필기 기준으로는 `@Autowired`로 클래스 필드를 이용해 값 주입이 가능하다는 점을 기억하면 된다. 📌

## 12. @Autowired 생성자 주입

생성자 주입은 생성자를 통해 필요한 의존성을 전달받는 방식이다.

예시는 다음과 같다.

    @Component
    public class Person {

        private final Parrot parrot;

        @Autowired
        public Person(Parrot parrot) {
            this.parrot = parrot;
        }
    }

스프링이 `Person` 타입 빈을 생성할 때 `@Autowired`가 붙은 생성자를 호출한다.  
그리고 생성자 매개변수로 컨텍스트에 있는 `Parrot` 타입 빈을 전달한다.

즉, 객체가 생성되는 순간 필요한 의존성이 함께 주입된다. ✅

## 13. 생성자 주입이 권장되는 이유

생성자 주입은 일반적으로 권장되는 의존성 주입 방식이다.

이유는 다음과 같다.

- 객체 생성 시 필요한 의존성을 명확히 알 수 있음
- `final` 필드 사용 가능
- 필수 의존성을 빠뜨리기 어려움
- 테스트 코드 작성이 쉬움
- 객체가 불완전한 상태로 생성되는 것을 막을 수 있음

즉, 중요한 의존성은 생성자 주입으로 받는 것이 좋다. 📌

## 14. Setter 주입

setter 메서드를 이용한 의존성 주입도 가능하다.

예시는 다음과 같다.

    @Component
    public class Person {

        private Parrot parrot;

        @Autowired
        public void setParrot(Parrot parrot) {
            this.parrot = parrot;
        }
    }

setter 주입은 객체 생성 후에 의존성을 주입한다.

필수 의존성보다는 선택적으로 바뀔 수 있는 의존성에 사용할 수 있다.

## 15. 순환 의존성

순환 의존성은 두 개 이상의 빈이 서로를 필요로 하는 상황이다.

예를 들어 다음과 같은 관계이다.

- `Parrot`을 만들려면 `Person`이 필요함
- `Person`을 만들려면 `Parrot`이 필요함

흐름은 다음과 같다.

1. 스프링은 `Parrot` 타입의 빈을 생성해야 한다.
2. `Parrot` 클래스 생성자를 호출하려면 스프링은 `Person` 타입의 빈이 필요하다.
3. 스프링은 `Person` 타입의 빈을 생성하려고 한다.
4. `Person` 타입의 빈을 생성하기 위해 스프링은 다시 `Parrot` 타입의 빈이 필요하다.

결국 스프링은 어떤 빈을 먼저 완성해야 할지 결정할 수 없어 교착 상태에 빠진다. ⚠️

## 16. 순환 의존성 해결 관점

순환 의존성은 설계상 문제가 있는 경우가 많다.

두 객체가 서로 반드시 필요하다면 책임이 잘 분리되어 있는지 확인해야 한다.

해결 방향은 다음과 같다.

- 의존 관계를 단방향으로 정리
- 공통 책임을 다른 객체로 분리
- 생성자 주입 구조에서 순환 참조 제거
- 정말 필요한 경우 지연 주입 방식 검토

시험 대비에서는 순환 의존성이 왜 문제가 되는지 흐름을 이해하는 것이 중요하다. 📌

## 17. @Qualifier로 대상 지정하기

같은 타입의 빈이 여러 개 있을 때는 `@Autowired`만으로 어떤 빈을 주입해야 할지 알 수 없다.

이때 `@Qualifier`를 사용해 주입할 빈의 이름을 지정한다.

형식은 다음과 같다.

    @Qualifier(value = "빈 이름")

예를 들어 생성자 주입에서 사용할 수 있다.

    @Component
    public class Person {

        private final Parrot parrot;

        @Autowired
        public Person(@Qualifier("miki") Parrot parrot) {
            this.parrot = parrot;
        }
    }

이 코드는 `Parrot` 타입 빈 중에서 이름이 `"miki"`인 빈을 주입한다. ✅

## 18. 중요 포인트 📌

- 스프링 빈 사이에도 관계를 설정할 수 있다.
- 사람이 앵무새를 소유하는 구조는 has-A 관계이다.
- `@Bean` 메서드 안에서 다른 `@Bean` 메서드를 호출해 빈 관계를 만들 수 있다.
- 스프링은 `@Bean` 메서드 호출을 관리하여 이미 존재하는 빈을 재사용할 수 있다.
- `@Bean` 메서드의 매개변수로 필요한 빈을 받아 와이어링할 수 있다.
- 와이어링은 빈 사이의 의존 관계를 연결하는 작업이다.
- IoC를 사용하지 않으면 애플리케이션이 직접 의존성을 생성하고 제어한다.
- IoC를 사용하면 프레임워크가 객체 생성과 의존성 연결을 제어한다.
- `@Autowired`를 필드에 붙이면 필드 주입이 가능하다.
- `@Autowired` 생성자 주입은 권장되는 방식이다.
- setter를 이용한 의존성 주입도 가능하다.
- 순환 의존성은 서로가 서로를 필요로 해서 빈 생성이 막히는 상황이다.
- 같은 타입 빈이 여러 개 있으면 `@Qualifier`로 주입 대상을 지정한다.

## 정리 ✅

스프링 컨텍스트에서 빈 작성은 단순히 객체를 등록하는 것뿐 아니라 빈 사이의 관계를 설정하는 과정까지 포함한다.  
`@Bean` 메서드 안에서 다른 `@Bean` 메서드를 호출하거나, `@Bean` 메서드의 매개변수로 빈을 받아 두 빈 사이의 has-A 관계를 만들 수 있다.  
스프링은 IoC 컨테이너로서 객체 생성과 의존성 연결을 직접 관리하며, `@Autowired`를 이용해 필드, 생성자, setter 방식으로 의존성을 주입할 수 있다.  
일반적으로 생성자 주입이 권장되며, 같은 타입의 빈이 여러 개 있을 경우 `@Qualifier`로 주입할 빈 이름을 지정해야 한다.  
또한 순환 의존성은 빈 생성 과정에서 교착 상태를 만들 수 있으므로 설계 단계에서 피하는 것이 중요하다.
